    Стандарты W3C: Свойство window.devicePixelRatio определено как одно значение с плавающей точкой.

    Зум: При pinch-zoom на мобильных устройствах devicePixelRatio не меняется, меняется только визуальный масштаб.

        baseZ++;

const zoomSteps = [];

Твоя идея сделать разное количество шагов для разных уровней — это решение двух проблем сразу:

    На рабочих зумах (14-18): Пользователю важна точность, чтобы идеально «вписать» объект в экран. Там можно сделать хоть по 20 шагов (изменяя размер тайла буквально по 5-10 пикселей за шаг).

    Калибровка «швов»: Ты можешь программно проверить весь массив один раз при запуске. Если какой-то scale дает дробный результат при умножении на 256 (из-за погрешности double), ты просто вручную или округлением поправляешь его в таблице.
    Эффект инерции: Имея массив индексов, очень легко реализовать «плавный стоп» (кинетический скролл). Ты просто продолжаешь менять индекс в массиве по инерции после того, как пользователь отпустил колесико или тачпад.
    Разный шаг для разных устройств: Для мышки можно прыгать через 2 элемента массива, а для тачпада (pinch-to-zoom) — идти по каждому элементу для идеальной плавности.

// Генерируем адаптивную таблицу

    let steps = (z >= 14 && z <= 18) ? 32 : 8;

        // И распределяем его равномерно между TILE_SIZE и TILE_SIZE * 2
        let size = Math.round(256 * Math.pow(2, i / steps));
        
        zoomTable.push({
            baseZ: z,
            scale: size / 256,
            realZ: z + Math.log2(size / 256)
        });
    }
}

  startX: 0, startY: 0
};

// --- ОБЩАЯ ФУНКЦИЯ ОТРИСОВКИ ---

  el.style.transform = `translate3d(${state.x}px, ${state.y}px, 0)`;
};

// --- ЛОГИКА ДЛЯ МЫШИ (ПК) ---
// Нюанс: используем document для надежности и меняем курсоры
const onMouseDown = (e) => {
  state.startX = e.clientX - state.x;
  state.startY = e.clientY - state.y;
  
  el.style.cursor = 'grabbing';

  const onMouseMove = (e) => {
    state.x = e.clientX - state.startX;
    state.y = e.clientY - state.startY;
    requestAnimationFrame(render);
  };

  const onMouseUp = () => {
    el.style.cursor = 'grab';
    document.removeEventListener('mousemove', onMouseMove);
    document.removeEventListener('mouseup', onMouseUp);
  };

  document.addEventListener('mousemove', onMouseMove);
  document.addEventListener('mouseup', onMouseUp);
};

// --- ЛОГИКА ДЛЯ TOUCH (МОБИЛЬНЫЕ) ---
// Нюанс: предотвращаем скролл и обрабатываем только один палец
const onTouchStart = (e) => {
  if (e.touches.length > 1) return; // Игнорируем мультитач, чтобы не мешать зуму
  
  const touch = e.touches[0];
  state.startX = touch.clientX - state.x;
  state.startY = touch.clientY - state.y;

    // чтобы случайное дрожание пальца не вызывало микро-сдвигов

    state.x = touch.clientX - state.startX;
    state.y = touch.clientY - state.startY;

    Производительность событий: На мобильных события touch генерируются с другой частотой, чем mouse. Разделив их, вы можете добавить фильтр низких частот или сглаживание только для пальца, чтобы движение не казалось дерганым из-за влажности кожи или дрожания рук.
    Passive Listeners: Для тач-событий критически важно управлять параметром { passive: false }, чтобы иметь возможность вызвать e.preventDefault(), если вы не хотите, чтобы страница скроллилась во время перетаскивания. Для мыши это обычно не требуется.

Если вы резко «кинете» карту, она продолжит движение. Это реализовано через физическое моделирование:

В отличие от нашего кода, где мы двигаем один элемент, Google Maps двигает контейнер с тайлами (плитками изображения/вектора): 

    Will-change: На контейнер карты жестко задано will-change: transform.
    Отложенная загрузка: Пока вы двигаете карту, новые данные (тайлы) могут не подгружаться мгновенно, чтобы не забивать поток JS. Активная загрузка и рендеринг тяжелых объектов (например, 3D зданий) часто приостанавливаются до завершения события dragend, чтобы сохранить стабильные 60 FPS.

Событие wheel работает независимо от состояния нажатия кнопок мыши:

    Если зажата любая кнопка мыши (или activePointers.size > 0):
        (Пункт 2) — Изменяем угол поворота (rotation). Колесо вверх — вправо, вниз — влево.
    Если кнопки не нажаты:
        (Пункт 3) — Изменяем масштаб (zoom/scale).

Почему именно так?

    Разделение Клика и Перемещения: Использование флага isMoving с порогом (threshold) — единственный надежный способ отличить намерение пользователя «нажать» от намерения «подвинуть», так как при касании пальцем координаты всегда немного дрожат.
    Мультитач (2 и 3 пальца): Проверка activePointers.size позволяет мгновенно переключать режим отрисовки. Для 2-х пальцев важно сохранять «начальное состояние» жеста (расстояние и угол), чтобы высчитывать дельту (разницу) в процессе движения.
    Изоляция Wheel: Событие wheel в браузерах генерируется отдельно. Проверка наличия активного pointerdown внутри обработчика wheel позволяет легко реализовать ваше условие (2) против (3).

В событиях указателя (
Pointer Events) каждое касание пальцем генерирует отдельное событие onpointermove со своим уникальным идентификатором pointerId. 
Свойства movementX и movementY наследуются от MouseEvent, но их использование для мультитача имеет особенности:
1. Как работают movementX/Y в мультитаче
При мультитаче браузер генерирует последовательные события для каждого пальца. 

    Для первого пальца: Событие pointermove придет с его pointerId и значением movementX/Y, рассчитанным относительно его предыдущей позиции.
    Для второго пальца: Сразу после этого (или в следующем кадре) придет другое событие pointermove с другим pointerId и своими значениями движения. 

2. Проблема надежности
Свойства movementX/Y могут вести себя нестабильно в разных браузерах (иногда они не определены или используют разные единицы измерения). Поэтому для мультитач-жестов (например, масштабирования или вращения) надежнее вычислять разницу координат самостоятельно. 
3. Рекомендуемый подход (через кэширование)
Для точного отслеживания движения каждого из двух пальцев сохраняйте их координаты в объекте или массиве:
javascript

const pointers = {}; // Хранилище активных касаний

el.onpointerdown = (e) => {
  pointers[e.pointerId] = { x: e.clientX, y: e.clientY };
};

el.onpointermove = (e) => {
  const prev = pointers[e.pointerId];
  if (prev) {
    // Вычисляем смещение для конкретного пальца (аналог movementX/Y)
    const movementX = e.clientX - prev.x;
    const movementY = e.clientY - prev.y;

    console.log(`Палец ${e.pointerId} сместился на:`, movementX, movementY);

    // Обновляем текущие координаты
    pointers[e.pointerId] = { x: e.clientX, y: e.clientY };

    // Если в объекте pointers 2 ключа — значит, сейчас активны два касания
    if (Object.keys(pointers).length === 2) {
      // Здесь можно обрабатывать логику зума или вращения
    }
  }
};

el.onpointerup = el.onpointercancel = (e) => {
  delete pointers[e.pointerId];
};

Используйте код с осторожностью.
Основные моменты:

    pointerId: Единственный способ отличить один палец от другого в общем потоке событий.
    isPrimary: Это свойство будет true только для первого коснувшегося пальца.
    CSS: Не забудьте добавить touch-action: none; элементу, чтобы браузер не перехватывал движение для прокрутки страницы.






Для создания собственной картографической библиотеки в 2025 году
однозначно стоит выбирать Pointer Events.
Хотя Touch Events кажутся «практичнее» из-за наличия массива всех пальцев в одном событии, современный стандарт Pointer Events предоставляет более гибкую и производительную архитектуру для сложных жестов (зум + вращение + панорамирование).
Вот детальное сравнение для разработчика библиотеки:
1. Почему Pointer Events лучше для архитектуры

    Унификация устройств: Вам не нужно писать разные ветки кода для тачпадов ноутбуков (которые эмулируют Pointer события с высокой точностью), стилусов и пальцев.
    Управление захватом (Pointer Capture): С помощью element.setPointerCapture(pointerId) вы можете «привязать» событие к элементу, даже если палец вышел за пределы карты во время резкого жеста. В Touch Events это реализовать сложнее.
    Производительность: Pointer Events позволяют избежать «превентивных» вызовов preventDefault(), которые часто замедляют прокрутку в мобильных браузерах. Вместо этого используется CSS touch-action: none;. 

2. Как реализовать мультитач (Зум и Вращение)
Вместо массива touches, вы создаете собственное состояние. Это дает вам полный контроль над тем, какой палец за что отвечает (например, игнорирование «случайного» третьего пальца).
Алгоритм для вашей библиотеки:

    Хранилище: Используйте Map для хранения координат активных указателей по их pointerId.
    Событие pointerdown: Добавляйте координаты точки в Map.
    Событие pointermove:
        Если в Map две точки:
            Вычисляйте расстояние между текущими позициями (для зума).
            Вычисляйте угол наклона вектора между этими точками относительно предыдущего кадра (для вращения).
            Вычисляйте центр масс (среднюю точку) между ними (для панорамирования во время зума).
        Обновляйте координаты в Map.
    Событие pointerup / pointercancel: Удаляйте ID из хранилища. 

3. Когда Touch Events всё же могут быть «проще»?
Единственный плюс Touch Events — это доступ к списку всех касаний (e.touches) в одном объекте события. Это позволяет не писать свой менеджер состояний. Однако: 

    В 2025 году многие браузеры на десктопах с тачскринами могут не поддерживать Touch API, но поддерживать Pointer API. Если вы выберете только Touch Events, ваша карта может не работать на Windows-ноутбуках с сенсорным экраном.
    Смешивать их (if (window.PointerEvent) ... else ...) — это путь к дублированию багов. 

Вердикт для библиотеки:
Используйте Pointer Events. Это даст вашей библиотеке: 

    Кросс-платформенность: Работа на ПК, планшетах, смартфонах и интерактивных панелях одним кодом.
    Будущее: Touch Events признаны устаревающими (legacy) для новых разработок.
    Точность: Возможность использовать данные о давлении или наклоне (например, для изменения угла обзора карты стилусом).



Отличный выбор! Это сделает архитектуру вашей библиотеки более современной и устойчивой к изменениям в стандартах браузеров.
Напоследок пара практических советов для реализации мультитача на Pointer Events:

    Нормализация координат: При расчете жестов всегда используйте clientX/Y или координаты относительно контейнера карты. Не полагайтесь на offsetX/Y, так как они могут вести себя непредсказуемо при быстром движении или наличии дочерних элементов (маркеров) на карте.
    Обработка pointercancel: Обязательно подписывайтесь на это событие. Оно срабатывает, если жест был прерван системой (например, выскочило уведомление или палец ушел за пределы экрана). Если его не обработать, в вашем Map (хранилище) останется «фантомный» палец, который сломает расчет зума.
    Порог (Threshold): Для плавности добавьте небольшой порог срабатывания (около 2-3 пикселей). Начинайте вращение или зум только после того, как пальцы разошлись на определенное расстояние, чтобы избежать «дрожания» карты от микро-движений кожи пальцев.
    Свойство isPrimary: Помните, что первый коснувшийся палец всегда имеет isPrimary: true. Это полезно, если вы захотите реализовать разное поведение для «главного» касания и вспомогательных.
