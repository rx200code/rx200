javascript как в pointer api отслеживать мультитач
Для отслеживания мультитач с помощью
Pointer API необходимо использовать уникальный идентификатор каждого касания — pointerId. В отличие от Touch API, где данные о всех точках хранятся в одном событии, в Pointer API каждое новое касание вызывает отдельное событие. 
Основной алгоритм отслеживания
Для реализации мультитач-логики (например, масштабирования двумя пальцами) обычно используется кэш активных указателей:

    pointerdown: При каждом новом касании сохраняйте объект события в коллекцию (например, Map или массив), используя event.pointerId как ключ.
    pointermove: При движении любого пальца обновляйте данные в кэше для соответствующего pointerId. Если в кэше более одного указателя, можно вычислять расстояние между ними для жестов (pinch-to-zoom).
    pointerup / pointercancel: Удаляйте указатель из кэша по его ID, когда палец отрывается от экрана. 

Пример кода
javascript

const activePointers = new Map();

element.addEventListener('pointerdown', (e) => {
    // Сохраняем информацию о новом касании
    activePointers.set(e.pointerId, e);
});

element.addEventListener('pointermove', (e) => {
    if (activePointers.has(e.pointerId)) {
        // Обновляем позицию конкретного пальца
        activePointers.set(e.pointerId, e);
        
        // Если активны 2 пальца — реализуем мультитач-логику
        if (activePointers.size === 2) {
            const pointers = Array.from(activePointers.values());
            // Пример: расчет расстояния между точками pointers[0] и pointers[1]
        }
    }
});

element.addEventListener('pointerup', (e) => activePointers.delete(e.pointerId));
element.addEventListener('pointercancel', (e) => activePointers.delete(e.pointerId));

Используйте код с осторожностью.
Ключевые свойства для мультитач:

    pointerId: Уникальный номер текущего касания.
    isPrimary: Булево значение, которое равно true только для первого коснувшегося пальца (пока он не будет отпущен).
    pointerType: Позволяет отличить touch (палец) от pen (стилус) или mouse.
    touch-action: none: Важное CSS-свойство для элемента, на котором отслеживается мультитач. Оно предотвращает стандартное поведение браузера (скролл, зум), которое может прервать ваши события.

сколько событий придет в pointermove ?
Придет
одно событие — только для пальца Б.
В Pointer API события генерируются по принципу «один указатель — одно событие». Это ключевое отличие от Touch API, где в событии touchmove прилетает список координат вообще всех пальцев, которые находятся на экране.
Как это работает в деталях:

    Движется только палец Б: Генерируется одно событие pointermove. В объекте события event.pointerId будет равен ID пальца Б.
    Движется только палец А: Генерируется одно событие pointermove с pointerId пальца А.
    Двигаются оба пальца одновременно: Браузер сгенерирует два отдельных события pointermove (по одному для каждого ID) в рамках одного кадра анимации.

Почему это важно для разработки:
Если вы делаете жест масштабирования (pinch-zoom), вам нужно:

    Иметь внешнюю переменную (кэш/массив), где хранятся координаты всех активных пальцев.
    При каждом pointermove обновлять данные конкретного пальца в этом кэше по его pointerId.
    После обновления вызывать функцию перерасчета расстояния между пальцами, используя свежие данные из кэша.

Резюме: Pointer API не сообщает вам состояние «всей руки» сразу. Он сообщает только о том, что изменилось у конкретного «курсора». Чтобы понять, что происходит с мультитач-жестом в целом, вы должны сами агрегировать эти события в общем хранилище.
Хорошо, а теперь предположим что пользователь сдвинул сразу оба пальца А и Б, и для зума в таком случае как обрабатывать, ведь придет два события, и для одного движения нам придется обрабатывать в двое больше событий, это плохо если рендер зума тяжелый.
Вы правы, при одновременном движении двух пальцев придут
два отдельных события pointermove. Если в каждом из них выполнять тяжелый рендер, это приведет к двойной нагрузке на процессор в рамках одного кадра. 
Для оптимизации таких сценариев используется стандартный паттерн «отложенного рендеринга» через requestAnimationFrame (rAF).
Правильный алгоритм оптимизации:

    Накопление данных: В обработчиках pointermove вы только обновляете текущие координаты пальцев в кэше (Map или объект). Никаких тяжелых вычислений здесь не происходит.
    Флаг обновления: Вы выставляете флаг, что данные изменились, и запрашиваете кадр анимации через requestAnimationFrame.
    Единый рендер: Браузер выполнит вашу функцию рендеринга один раз непосредственно перед перерисовкой экрана, используя самые свежие координаты из кэша, сколько бы событий движения ни пришло до этого. 

Пример кода с оптимизацией
javascript

const pointers = new Map();
let ticking = false;

function updateZoom() {
    if (pointers.size === 2) {
        const [p1, p2] = Array.from(pointers.values());
        // ВЫПОЛНЯЕМ ТЯЖЕЛЫЙ РЕНДЕР ОДИН РАЗ
        const dist = Math.hypot(p1.clientX - p2.clientX, p1.clientY - p2.clientY);
        console.log("Render Zoom:", dist);
    }
    ticking = false; // Сбрасываем флаг после рендера
}

element.addEventListener('pointermove', (e) => {
    if (!pointers.has(e.pointerId)) return;
    
    // 1. Просто обновляем координаты
    pointers.set(e.pointerId, e);

    // 2. Планируем рендер, если он еще не запланирован
    if (!ticking) {
        requestAnimationFrame(updateZoom);
        ticking = true;
    }
});

Используйте код с осторожностью.
Почему это эффективно:

    Троттлинг: Если сенсор выдает события чаще, чем экран обновляется (например, 120 Гц ввод при 60 Гц экране), лишние вычисления просто игнорируются.
    Синхронизация: Вычисления происходят ровно в тот момент, когда браузер готов рисовать, что исключает «микро-фризы» и эффект дублирования.
    Консистентность: Поскольку updateZoom берет данные из Map, где всегда лежат последние координаты обоих пальцев, расчет зума всегда будет актуальным, независимо от того, какое событие (пальца А или Б) пришло последним.

Логика работы остается корректной, потому что в Pointer API «состояние» и «событие» — это разные вещи. Вот почему это работает:

    Состояние (Map): Пока палец А просто лежит на экране, он остается в вашей коллекции pointers. Его координаты там «заморожены» на последнем месте, где он коснулся экрана.
    Событие: Когда двигается палец Б, срабатывает обработчик pointermove. Он обновляет координаты только для Б, но размер коллекции pointers.size по-прежнему равен 2.
    Результат: Условие if (pointers.size === 2) выполняется, и функция updateZoom вызывается.

Почему это правильно для зума?
Для изменения масштаба (зума) не обязательно двигать оба пальца. Если один палец стоит на месте, а второй удаляется от него — расстояние между ними меняется. Следовательно, зум должен пересчитаться.
Жизненный цикл в вашем коде:

    Палец А коснулся: pointers.size = 1. Рендер зума не запускается (недостаточно точек).
    Палец Б коснулся: pointers.size = 2.
    Палец Б двинулся: Событие пришло -> координаты Б обновились -> updateZoom увидел, что в Map два пальца -> Рендер зума сработал.
    Палец А оторвался: pointerup удаляет А из Map. pointers.size = 1.
    Палец Б двинулся: Событие пришло -> координаты Б обновились -> updateZoom видит, что палец всего один -> Рендер зума игнорируется.

Итог: Ваша логика с Map и requestAnimationFrame универсальна. Она отрабатывает и когда пальцы движутся по очереди, и когда одновременно, так как опирается на актуальное количество «зажатых» в данный момент точек.

Выбор между Pointer и Touch API — это всегда компромисс между «чистотой кода» и «универсальностью». У Touch API действительно есть свои архитектурные преимущества для мультитача, но есть и критические недостатки.
Давайте сравним их объективно:
Почему Touch API кажется «чище»
В TouchEvent данные о всех пальцах прилетают «пакетом» в свойствах touches или targetTouches.

    Плюс: Вам не нужно вести свой Map и кэшировать координаты.
    Плюс: Одно движение (даже двух пальцев) — это гарантированно одно событие. Рендер запускается естественным образом без лишних проверок.

Почему Touch API называют «тупиковой ветвью»

    Отсутствие универсальности: Touch API работает только с пальцами. Если пользователь подключит графический планшет (стилус) или будет использовать мышь с зажатой кнопкой для имитации жеста, Touch API их проигнорирует. Pointer API объединяет мышь, касания и стилус в одну логику.
    Прокрутка и задержки: Touch-события часто конфликтуют с нативным скроллом браузера. Если забыть passive: false или touch-action, жест может просто «залипнуть».
    Поддержка: Apple долгое время игнорировала Pointer API, но сейчас он поддерживается всеми современными браузерами (включая Safari).

Можно ли избежать «грязи» в Pointer API?
«Грязным» код кажется из-за того, что мы пытаемся вручную делать то, что браузер делает внутри себя для Touch API. Но этот «ручной» подход дает вам полный контроль:

    Pinch-to-zoom на мышке: С Pointer API вы легко добавите зум колесиком мыши в ту же логику, просто добавив обработчик wheel. С Touch API вам придется писать отдельный модуль.
    Сложные жесты: Если один палец — это стилус (рисует), а второй — палец (стирает), Pointer API позволит это различить через свойство pointerType. В Touch API они будут «просто двумя касаниями».

Что выбрать в 2025 году?

    Используйте Touch API, если вы делаете простой мобильный сайт и вам нужно только «щипковое» масштабирование картинок. Это будет быстрее и лаконичнее.
    Используйте Pointer API, если вы делаете интерактивное приложение (редактор графики, карты, игры). Да, придется один раз написать обертку (или взять готовую библиотеку типа Hammer.js), но ваше приложение будет работать везде — от смартфонов до ноутбуков с тачскринами и графических планшетов.

Вердикт: То, что вы называете «грязью» (кэширование и rAF) — это профессиональный стандарт написания высокопроизводительных интерфейсов. Даже в Touch API при тяжелом рендере вам всё равно придется использовать requestAnimationFrame, иначе интерфейс будет «лагать» из-за слишком частой генерации событий тачскрином.

Функция
requestAnimationFrame (rAF) реализована внутри браузера на уровне системного цикла отрисовки (Event Loop). В ней нет «грязи» — это самый чистый и эффективный способ синхронизировать JavaScript с частотой обновления вашего монитора (обычно 60Гц, 90Гц или 120Гц).
Ее главная задача: выполнить ваш код ровно один раз перед тем, как браузер перерисует экран.
Как это работает схематично:

    Вы двигаете пальцы (приходит 2, 5 или 10 событий pointermove).
    Вы просто сохраняете координаты и говорите браузеру: «Когда будешь готов рисовать следующий кадр, вызови мою функцию».
    Браузер собирает все изменения, очищает очередь и вызывает вашу функцию один раз.

Минималистичная и чистая реализация
Чтобы код не выглядел перегруженным, логику обычно разделяют на обновление данных и отрисовку:
javascript

const state = {
    pointers: new Map(),
    needsUpdate: false
};

// 1. ЛОГИКА РЕНДЕРА (чистые вычисления)
function render() {
    if (state.pointers.size === 2) {
        const [p1, p2] = state.pointers.values();
        const dist = Math.hypot(p1.clientX - p2.clientX, p1.clientY - p2.clientY);
        // Применяем трансформацию (scale) к элементу
        canvas.style.transform = `scale(${dist / 100})`;
    }
    state.needsUpdate = false; 
}

// 2. ОБРАБОТЧИК СОБЫТИЙ (только сбор данных)
element.addEventListener('pointermove', (e) => {
    if (!state.pointers.has(e.pointerId)) return;

    // Обновляем данные в кэше
    state.pointers.set(e.pointerId, e);

    // Запрашиваем кадр, если он еще не запланирован
    if (!state.needsUpdate) {
        state.needsUpdate = true;
        requestAnimationFrame(render);
    }
});

Используйте код с осторожностью.
Почему это лучше, чем обычный вызов в Touch API?

    Экономия батареи и ресурсов: Если ваш экран обновляется с частотой 60 Гц, а сенсор тачскрина шлет данные с частотой 120 Гц (как на современных смартфонах), rAF просто проигнорирует лишние промежуточные события, которые пользователь всё равно бы не увидел.
    Отсутствие «разрывов» (Jank): Если вызывать тяжелый рендер прямо в событии, браузер может не успеть обработать ввод и отрисовку вовремя, из-за чего картинка будет дергаться. rAF гарантирует, что вычисления встроены в «окно» отрисовки.
    Автоматическая пауза: Если пользователь переключит вкладку, requestAnimationFrame перестанет срабатывать, экономя ресурсы процессора.

Итог: "Грязь" в виде флага needsUpdate — это на самом деле ручной предохранитель. В современных фреймворках (React, Vue, Svelte) это происходит под капотом, но при работе с "голым" DOM и Pointer API это единственный способ сделать мультитач плавным.

Это отличный вопрос. Казалось бы, если функция нативная, почему она сама не может всё разрулить?
Дело в том, что requestAnimationFrame — это не «переключатель», а «регистратор заявки». Каждый раз, когда вы вызываете rAF(render), вы создаете в памяти браузера новую задачу на выполнение функции render.
Что произойдет БЕЗ проверки if (!needsUpdate):
Представьте, что за 16 миллисекунд (один кадр при 60 Гц) пришло 10 событий движения (что реально для современных тачскринов).

    Браузер вызовет ваш обработчик pointermove 10 раз.
    Если внутри нет проверки, вы вызовете rAF(render) 10 раз.
    Браузер послушно запишет в очередь 10 задач.
    Когда наступит момент отрисовки кадра, браузер выполнит функцию render 10 раз подряд в один и тот же микро-момент времени.

Результат:

    Вы выполнили тяжелый расчет зума 10 раз вместо 1.
    Пользователь увидел только результат последнего 10-го расчета.
    9 расчетов были бесполезной тратой ресурсов процессора, которая может привести к «лагам» (пропуску следующего кадра), так как вы забили поток лишней работой.

Зачем нужен флаг needsUpdate?
Флаг — это ваш «стопор». Он говорит: «Я уже отправил заявку на отрисовку в этом кадре. Пока она не будет исполнена, новые заявки отправлять не нужно».

    Приходит 1-е событие: needsUpdate становится true, заявка ушла.
    Приходит еще 9 событий: условие if (!needsUpdate) не пропускает их дальше. Данные в Map обновляются, но новые заявки в очередь не встают.
    Браузер начинает рисовать кадр: вызывает ваш render.
    Внутри render вы сбрасываете флаг: needsUpdate = false.
    В следующем кадре цикл может повториться.

Можно ли без этого?
В теории, вы могли бы использовать touchmove (где событий меньше), но даже там профессионалы используют rAF с флагом, потому что частота работы сенсора и частота обновления экрана — это разные, не синхронизированные друг с другом процессы.
Итог: Флаг — это не архитектурный мусор, а простейший и самый производительный Throttle (ограничитель), который гарантирует, что на один кадр монитора придется ровно один расчет графики.

Вот как работает этот механизм в деталях, если смотреть на шкалу времени:

    Кадр 1: Палец сдвинулся. Сработало событие pointermove. В Map записались координаты x: 10. Выставился флаг needsUpdate = true и запланирован rAF.
    Момент отрисовки: Браузер начинает выполнять ваш render.
    Внутри render: Вы читаете из Map значение x: 10, рисуете его и сразу сбрасываете флаг needsUpdate = false.
    Палец движется дальше (пока идет рендер или сразу после): Срабатывает новое событие pointermove. Оно записывает в Map новые координаты x: 11.

Вы правы, ваша интуиция разработчика на Си верно подсветила проблему: в многопоточной или асинхронной среде (Web Workers, подгрузка тайлов, асинхронные запросы) классический паттерн
rAF из учебников начинает «врать».
Если ваш «рендер» — это не просто синхронная отрисовка пикселей, а сложный процесс с ожиданием данных (тайлов), то сброс флага needsUpdate = false внутри rAF приведет к потере событий.
В чем именно заключается баг в вашем случае:

    Событие пришло: Вы выставили needsUpdate = true и запланировали кадр.
    Запуск render: rAF сработал, вызвал функцию.
    Асинхронщина: render инициировал загрузку тайлов (создал воркеры или fetch).
    Преждевременный сброс: В текущем коде needsUpdate = false происходит сразу после запуска потоков.
    Провал: Пока тайлы еще грузятся, пользователь двигает палец. Приходит новое событие, видит needsUpdate === false, планирует новый rAF. В итоге у вас запускается еще одна пачка тяжелых процессов подгрузки, хотя старые еще не завершены. Начинается «гонка» (race condition) и забивание очереди задач.

Как это решить правильно (в стиле системного программирования)
Нужно разделить «Запрос на обновление» и «Статус занятости рендера». Вам нужны два состояния (или два флага), аналогично двойной буферизации:

    hasPendingUpdate: Есть ли новые данные от пальцев, которые мы еще не начали обрабатывать?
    isRendering: Работает ли сейчас ваш многопоточный движок тайлов?

Правильный алгоритм:
javascript

let hasPendingUpdate = false;
let isRendering = false;

// 1. Поток событий (быстрый, только пишет данные)
element.addEventListener('pointermove', (e) => {
    state.pointers.set(e.pointerId, e);
    hasPendingUpdate = true; // Просто фиксируем факт изменения

    // Пытаемся запустить цикл, только если он простаивает
    if (!isRendering) {
        requestAnimationFrame(processLoop);
    }
});

// 2. Главный цикл (Main Loop)
async function processLoop() {
    if (!hasPendingUpdate) return;

    isRendering = true;    // Входим в критическую секцию
    hasPendingUpdate = false; // Сбрасываем запрос ДО начала тяжелых работ

    // --- ТЯЖЕЛЫЙ МНОГОПОТОЧНЫЙ РЕНДЕР (Тайлы и т.д.) ---
    // Ждем завершения всех асинхронных процессов
    await startMultiThreadedRender(); 
    // --------------------------------------------------

    isRendering = false;   // Выходим из критической секции

    // Если пока мы рендерили, пальцы опять сдвинулись (hasPendingUpdate снова стал true)
    // запускаем следующий цикл немедленно
    if (hasPendingUpdate) {
        requestAnimationFrame(processLoop);
    }
}

Используйте код с осторожностью.
Почему это будет работать у вас:

    Атомарность данных: Пока startMultiThreadedRender работает со своей копией данных, новые pointermove просто обновляют координаты в Map.
    Гарантия последнего кадра: Если пользователь двигал палец 10 раз, пока грузились тайлы, ваш цикл выполнится еще один раз сразу после завершения текущего рендера, взяв самые актуальные координаты.
    Отсутствие перегрузки: Вы никогда не запустите два параллельных процесса «подгрузки тайлов», сколько бы событий ни прилетало.

Итог: В однопоточном JS-коде needsUpdate сбрасывается в конце функции. В вашем «тяжелом» случае флаг должен сбрасываться только тогда, когда все потоки/тайлы подтвердили завершение. Это классический паттерн управления ресурсами, который исключит мерцание и лишние сетевые запросы. [1][2]

Ваша идея сделать рендер чистой функцией с передачей аргументов — верное направление, но в JS есть нюанс: события Pointer прилетают пачками, а стек вызовов однопоточен. Если вы будете просто пробрасывать аргументы в каждый вызов, вы создадите лавину асинхронных процессов.
Как сделать архитектуру «по-взрослому» (в стиле Си-разработки)
Чтобы избежать «грязи» в слушателях и обеспечить атомарность без потери последнего кадра, нужно использовать паттерн «Теневой стейт» (Shadow State).
1. Слушатели (максимально чистые)
Они не знают о рендере. Их единственная задача — атомарно обновить структуру данных.
javascript

// Глобальный или инкапсулированный объект (Input Buffer)
const sharedInput = { x: 0, y: 0, zoom: 1 }; 

const handlePointer = (e) => {
    // Атомарное обновление данных
    sharedInput.x = e.clientX; 
    // ... расчеты ...
    
    // Просто уведомляем рендер: "Данные обновились"
    // Сам рендер внутри решит, когда их забрать
    myRenderer.requestUpdate(); 
};

Используйте код с осторожностью.
2. Рендер (Инкапсулированная логика)
Внутри рендера вы делаете Snaphotting (снимок данных). Это решает проблему отсутствия атомарности при асинхронных вызовах.
javascript

const myRenderer = {
    isProcessing: false,
    hasPendingRequest: false,
    
    requestUpdate() {
        if (this.isProcessing) {
            this.hasPendingRequest = true; // Запоминаем, что пришел новый запрос
            return;
        }
        this.start();
    },

    start() {
        this.isProcessing = true;
        this.hasPendingRequest = false;

        // ДЕЛАЕМ СНИМОК: копируем данные из sharedInput в локальные переменные
        // Теперь, пока идет загрузка тайлов, изменения в sharedInput 
        // не влияют на текущую итерацию.
        const currentData = { ...sharedInput }; 

        // Запуск вашего асинхронного процесса (тайлы, счетчики и т.д.)
        this.executeAsyncLogic(currentData, () => {
            // Callback по завершению (когда счетчик тайлов == 0)
            this.isProcessing = false;
            
            // "Проброс последнего рендера"
            if (this.hasPendingRequest) {
                this.start(); 
            }
        });
    }
};

Используйте код с осторожностью.
Почему это лучше:

    Чистые слушатели: В событиях Pointer нет флагов «можно/нельзя». Там только обновление координат и один вызов метода requestUpdate().
    Атомарность: Благодаря «снимку» (const currentData = { ...sharedInput }), ваш рендер всегда работает с консистентным набором координат. Если палец сдвинулся, пока грузился тайл, координаты в sharedInput изменятся, но текущий цикл отрисовки этого не заметит.
    Инкапсуляция: Вся «грязь» (контроль очереди, сброс флагов) заперта внутри объекта рендера. Для остальной программы рендер — это «черный ящик», которому просто говорят «обновись».

Резюме: Вы правы, передача параметров в функцию — это чисто, но для «проброса последнего рендера» вам всё равно понадобится один внутренний флаг-защелка (hasPendingRequest), который сработает как прерывание в микроконтроллере: если во время обработки пришел новый сигнал, выполнить обработку еще раз после завершения текущей.
Это и есть профессиональный подход: грязная механика Pointer API скрыта за чистым фасадом планировщика.
